# VIvian V1.0：整合复核与第一阶段实施任务

日期：2026-11-03；版本：0.1；状态：文档复核完成，真实引擎兼容性未验证。

## 1. 本轮结论

可以开始限定范围的技术验证（Spike）、模拟引擎与基础工程；不能按现有十份文档直接全面开发或发布。C-1～C-5 仍为 Open。本文件是整合修订建议及下一阶段执行依据，不是实机通过证明，也不是完整冻结架构。

保留三游戏、独立进程适配、串行调度、中文 WPF 界面、运行记录、配置保护、版本检测和可恢复更新的方向。优先验证结果证据与停止控制，避免先做大量界面，再发现底层无法可靠控制。

## 4. 技术与产品裁决建议

### 4.1 技术栈

保留 C# / .NET 10 / WPF / SQLite。先锁定 SDK 与依赖版本并验证 WPF-UI；首个原型不要求单文件、裁剪或复杂材质效果。

微软官方支持表显示 .NET 8 于 2026-11-10 结束支持，.NET 10 支持至 2028-11-14。因此在本项目日期下，不采用“为与上游一致而改用 .NET 8”的建议。进程外集成不要求主程序与引擎使用同一运行时。目标 Windows 版本支持范围还需单独确认，不把所有 Windows 10/11 版本都标记已支持。

来源：https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core

### 4.2 结果、生命周期和清理状态分离

| 层 | 建议值 | 用途 |
|---|---|---|
| 执行阶段 | Pending / Preflight / Starting / Running / Stopping / Reconciling / Finished / Blocked | 现在执行到哪里 |
| 任务结果 | Success / Failed / Cancelled / Indeterminate（运行中为空） | 任务结果是什么 |
| 清理结果 | NotRequired / Pending / Confirmed / Unconfirmed | 是否已解除运行占用 |

每次结果保存 RunId、适配规则版本、引擎指纹、配置摘要、证据引用和原因码。结果可为 Success 但清理 Unconfirmed，此时仍禁止下一任务。

成功至少要求：明确的本次运行关联、实际任务与所选配置一致、计划内任务的完成证据、没有未解决的终态失败/取消/冲突。不能用“没有错误”“游戏已关闭”“父进程0退出”替代成功证据。无法验证任务级覆盖时，明确缩小支持范围或标记未知。

旧日志、其他实例、截断 JSON、晚到事件、日志轮转、PID 复用均纳入模拟测试。用户手动确认保存为独立备注，不能改写自动判定证据。

失败后继续下一游戏的前提是清理已确认。无法停止、身份不明、锁状态不明时阻断整条队列；不能“等待10秒后继续”。

### 4.3 三引擎专项

- M7A：优先核实发行包真实 CLI 与 run JSON；按本次运行 ID 关联，禁止以 latest 直接关联。关于 auto_update/check_update 的含义按固定源码重新核实；此前批量设置 auto_update=false 的方案撤出实施清单。不得伪造首次免责声明确认。
- BetterGI：核实配置名选择、任务级结果与多实例日志关联；错误配置必须在真正发出游戏操作前被拒绝。无可靠外部结果接口时不能只靠“结束”字符串声称日常完成。
- ZZZ：核实启动器、提权后执行进程、代码同步与实例配置。auto_update_code/force_update 只是待核实键，不立即写入用户配置。23001 后端及 /health、/game/status 都须先证明在该发行包存在；V1 不以它们必然可用为前提。

### 4.4 权限、互斥与停止

先用测试进程验证提权执行器方案，比较启动方式、Job 加入时机、嵌套/脱离、句柄继承、拒绝 UAC、UI 死亡及执行器死亡。只有被证明确实归属本次运行的进程才可自动停止；普通扫描不能提供强隔离保证。

命名锁遇到拒绝访问、命名对象冲突、遗弃状态时进入对账，不能视为“没有别人在运行”。无控制能力的人工引擎不强行接管。普通权限进程并不等同于安全沙箱；探针同样是执行外部代码，优先静态检查，动态探针在隔离测试环境进行。

### 4.5 更新与恢复

V1 先实现版本检查、兼容状态、保留上一代和用户发起的受控切换。自动适配上游仍是长期目标，当前不承诺发布即兼容。

兼容状态采用 Verified / Unverified / Incompatible；未知版本不等于已知坏版本，但默认不进入统一执行队列。规则包作为受限数据处理，不下载任意脚本执行。

官方资产哈希用于完整性核对；同一上游仓库里的 API 与发行说明不能算独立信任源。VIvian 自签清单表达本项目对精确资产的认可，不能冒充上游签名。签名、来源真实性和功能兼容是三种不同检查。

代码、运行时、模型、配置分别记录版本与恢复范围。写前保留快照，临时目录验证后再提交，故障恢复根据事务记录选择继续或回退。不能盲目合并 YAML 默认值，也不能用新配置覆盖旧版回滚配置。

### 4.6 隐私与许可证

默认只保存必要日志；失败截图优先限定游戏窗口，本地保存并可关闭。导出采用字段白名单并预览；不声称正则能完全识别所有敏感内容。用于恢复的配置快照必须保真并受访问保护，不能为脱敏而破坏恢复；脱敏仅作用于诊断副本。

原 license_and_risk.md 把 GPL 与禁止商业售卖混同。GNU 明确允许有偿分发；不能一边声称按 GPL 发布，一边据此添加统一的非商业限制。项目可以免费提供，但项目声明、许可证、商标与游戏条款应分别核查，不作“采用 GPL 即消除全部争议”的承诺。RELEASE_GATES 的“30天内可获取源码”也不应直接作为通用合规标准。

本轮只纠正这一原则性错误，不对三个具体发行包给出法律合规通过结论。V1 默认不捆绑引擎，不自动删除用户安装中的附属组件；不启用内存修改功能。最终许可证及分发材料仍需按实际依赖和发布方式核查。

来源：https://www.gnu.org/philosophy/selling.en.html

## 6. 可直接交给本地 Codex 的任务指令

项目名严格使用 VIvian。工作目录为用户提供的 E:\auto agent game；先检查现有文件和仓库状态，保留原始十份报告，不覆盖。以本整合复核说明作为冲突修订基线。

本阶段只做 S0～S3 的验证工程，放入独立 spikes/ 目录。不要把未验证的 CLI、配置键、端口或版本结论写成生产适配器。先做不启动真实引擎的工作，再准备可审查的实机验证步骤；真实游戏启动、UAC、游戏设置更改仍需对应明确授权。

1. 生成 docs/evidence/EVIDENCE_INDEX.md：每个上游结论关联完整 commit、源码路径、官方资产、SHA-256、获取时间、证据级别。未取得证据写 Pending，不能伪造“已验证”。
2. 生成 docs/architecture/DECISIONS.md：统一结果/生命周期/清理状态、权限候选、进程身份、互斥、配置事务、恢复协议。记录替代方案及未验证项。
3. 建立 FakeEngine 与隔离测试：覆盖0退出缺证据、失败记录与成功文本冲突、旧日志、取消、父退子存活、迟到事件、配置并发更改、未知版本、停止失败、重启对账。未知不能冒充失败或成功；清理未确认不能继续队列。
4. Windows原型先用专用测试进程验证Job与提权链，覆盖UI被杀、执行器被杀、子进程脱离、拒绝UAC、PID复用、重复开始。禁止按进程名结束已有真实引擎或游戏。
5. 核实后才生成三引擎动态验证步骤；不要猜测 dry-run、/health、/game/status 等接口存在。错误配置测试先用副本与安全条件，防止静默执行真实任务。
6. 配置补丁只作用于测试副本；冲突时中止并保留新内容。首次声明和登录不自动确认。通过后才讨论生产配置托管。
7. 每项输出命令、退出码、标准流、运行关联、测试前后文件摘要、环境、结果及限制。日志脱敏副本可交付，原始敏感数据留本地。
8. 交付 docs/acceptance/SPIKE_RESULTS.md、docs/reviews/OPEN_BLOCKERS.md、测试源码和实际构建/测试日志。无Windows环境则完成可执行的离线部分，并明确列出未执行项。

阶段出口：C-1～C-5逐项有证据或明确不可行结论；不可行也算验证成果，但不算发布通过。停止验证工程后形成审查材料，不跳过审查连续开发全部M1～M6。

## 7. 实机记录最小模板

| 字段 | 要求 |
|---|---|
| CaseId / RunId | 唯一且可关联原始输出 |
| Environment | OS构建、会话、权限、DPI、引擎及游戏版本 |
| Provenance | 完整提交、资产名称/URL/哈希、规则版本 |
| Preconditions | 配置快照、已有进程清单、隔离边界 |

| Observation | 时间戳、退出码、子进程归属、日志/结构化记录 |
| Expected / Actual | 分列记录，不把预期复制为实测 |
| Verdict | Pass / Fail / Pending / NotApplicable及原因 |
| Cleanup | 已确认/未确认；任何用户数据变更 |
