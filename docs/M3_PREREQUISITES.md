# VIvian M3 前置清单：接入三款真实引擎之前必须具备的条件

日期：2026-11-03　依据：`docs/reference/INTEGRATED_REVIEW.md` §4–§6、`docs/M2_ACCEPTANCE.md` §8

> **状态更新（2026-11-04，只补充，不改动下表）**：C2 已由 PR #14 合并；C3 已由 PR #13 合并；C5 的证据索引已建立（`evidence/EVIDENCE_INDEX.md`），其中多数条目仍为 Pending；C1 的无害权限探针已随 PR #35 合并（PR #23），桌面 UAC 验证仍 Pending（#16）；D3 已完成：评审发现的 Critical/High 问题已在 PR #30、#33（含 #20）中修复并经 Codex 验收。B1 的星铁部分已有官方发布元数据与只读核对工具，官方包实际文件仍待核验（#25）。A 节与 B2～B12 全部未完成。当前进度见 [`README.md`](README.md) 第 5 节。

M3 的目标是把 BetterGI（原神）、March7thAssistant（星穹铁道）、ZenlessZoneZero-OneDragon（绝区零）接入 M2 的执行内核。下表中的条件没有满足之前，**不编写生产适配器**，不把未经验证的命令行参数、配置键、端口或结束信号写进产品代码。

## A. 需要用户提供或决定的事项

| # | 事项 | 原因 | 状态 |
|---|---|---|---|
| A1 | 一台 Windows 10/11 x64 测试电脑，已安装三款游戏和三款引擎 | 云端环境和 CI 机器无法运行游戏 | ⏳ 待用户确认 |
| A2 | 明确授权：允许在测试电脑上启动游戏和引擎、处理 UAC 提示、修改**测试副本**的配置 | `INTEGRATED_REVIEW.md` §6 的要求：实机操作必须有明确授权 | ⏳ 待授权 |
| A3 | 使用哪些游戏账号做测试，由用户自行决定 | 第三方自动化存在账号处罚风险，VIvian 无法保证不受处罚 | ⏳ 用户决定 |
| A4 | 在测试电脑上由谁执行验证：用户按步骤手动操作，或者让 Claude 通过桌面应用连接这台电脑执行 | 影响验证步骤怎么写 | ⏳ 待确认 |
| A5 | 仓库保持公开还是改为私有 | 安全与隐私考虑 | ⏳ 待用户决定 |

## B. 每款引擎都必须实测并记录证据的项目

证据按 `INTEGRATED_REVIEW.md` §7 的模板记录：固定的完整提交号或发行包哈希、实际命令、退出码、原始输出、前后文件摘要、限制。

| # | 验证项 | 为什么关键 |
|---|---|---|
| B1 | 固定版本：发行包名称、下载地址、SHA-256、对应源码提交 | 后续结论只对这一版本成立 |
| B2 | 无界面启动方式和真实可用的命令行参数 | 不能猜测 `--dry-run`、`/health` 之类的接口 |
| B3 | **进程树**：引擎会拉起哪些进程，游戏是不是引擎的子进程，有没有经过启动器、服务或 `ShellExecute` | 决定 Job Object 能否覆盖游戏；覆盖不到就会出现“清理已确认、游戏仍在运行” |
| B4 | **权限**：引擎或游戏是否需要管理员权限 | 提权的进程会脱离普通权限创建的 Job（D04） |
| B5 | **完成证据**：哪个日志、JSON 或退出状态能证明“本次运行的计划任务已完成”，能否关联到本次运行 | VIvian 只认本次 RunId 的明确证据 |
| B6 | **失败与取消证据**：明确的失败、取消输出 | 避免按关键词一票否决（D02） |
| B7 | **正常停止方式**：引擎有没有可以请求它正常结束的方法 | 没有的话，只能在超时后终止整个 Job，游戏会被强制关闭 |
| B8 | 输出位置：标准输出，还是日志文件；日志按什么规则轮转 | 卡死检测和证据来源都依赖它 |
| B9 | 单实例行为：引擎已经在运行时再次启动会怎样 | 防止参数被忽略、误判为成功（D05） |
| B10 | 首次运行的声明、登录等提示 | 不允许自动代替用户确认 |
| B11 | 配置文件的位置和格式；VIvian 是否需要修改它；若需要，在**副本**上验证冲突保护 | D07：冲突时保留用户的最新内容 |
| B12 | 中文、空格路径下能否运行 | D11：按实测结果接受或给出解释性拒绝 |

## E. 建议的 M3 推进顺序

1. 用户完成 A1～A5 的确认。
2. 先做 C1（提权原型）和 C2，不涉及真实游戏。
3. 在测试电脑上逐款完成 B1～B12，**每次只验证一款引擎**，先用测试副本。
4. 证据评审通过后，才为该款引擎编写生产适配器；每款引擎一个 PR，按 M2 的方式通过 CI。
5. 三款都完成后，再做真实队列的人工验收。

只要有一项验证结果为“不可行”，那一款引擎就缩小支持范围，或者在界面上标明不支持。**不能把“不可行”写成“已完成”。**
